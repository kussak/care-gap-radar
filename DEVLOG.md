# DEVLOG

Notes on building this project with an AI collaborator (Claude Code): what worked, what it got wrong, and what I corrected.

> First draft generated by Claude from the session history at my request, then reviewed and edited by me.

**Timeline:** Friday 2026-10-30 to Sunday 2026-11-01: 7 phases plus worklist refinements, 19 commits.
**API spend:** one real Claude call (about 1,400 input and 900 output tokens), well under a cent. Every test runs against a fake provider.

**How we worked:** CLAUDE.md held the spec and the working agreements. Claude had to:
- state a plan before each phase;
- stop after each phase for my OK;
- ask about clinical logic instead of guessing;
- never change a definition silently.

Most of the interesting moments below came from those stop-and-report points.

## Phase 0: Spec review and environment

**What happened**
- I asked Claude to review CLAUDE.md before writing any code.
- It found real gaps and contradictions in my spec:
  - "Active diagnosis" was undefined.
  - It wasn't clear whether prediabetes counts as diabetes.
  - The spec banned exact age in prompts, but its own example fact was "Age 55" (exact). Should it be a band instead?
  - The brief cache key didn't include the prompt version, so a changed prompt would serve stale briefs.
  - The 80-word outreach limit wasn't enforced anywhere.

**What I decided**
- An active diagnosis started before the index date and hasn't stopped.
- Prediabetes is excluded.
- Ages are 10-year bands ("Age 55–64").
- The cache key includes the prompt version, and validation enforces the 80-word limit.

These went into CLAUDE.md as a separate docs commit.

**What Claude got wrong**
- **It twice reported that `uv` and Java 17 weren't installed.** They were. Its tool shell had a stale PATH. I had to tell it to check `java --version` and to "reload the shell". The fix was to run every command through a login shell (`bash -lc`); it saved that as a memory note.
- On the Intel Mac, `uv` resolved ancient versions of `numba` and `shap`. Claude fixed this with version constraints in `pyproject.toml`.
- It accidentally committed dbt's `.user.yml` and my `.vscode/settings.json`. It caught both and removed them from the commit.

**What I corrected:** my `.ant-key` placeholder file. The key belongs in `.env`, which is gitignored.

## Phase 1–2: Scaffold, Synthea, staging

**What happened**
- Generated 2,000 patients in Chicago with a fixed seed.
- Claude inspected the real CSV headers before writing any SQL, as CLAUDE.md requires.
- The staging models drop SSN and address at the first step.

**Surprises:**
- Synthea data runs up to the day it was generated (2026-10-30) and covers whole lifetimes.
- Timestamps are in UTC.
- Synthea has a "Dual Eligible" payer, which we mapped to Medicare because Medicare pays first for dual-eligibles.

## Phase 3: Features, care gaps, labels

**What happened**
- Built index dates (current, test = −6 months, train = −12 months), the population, features, care gaps and labels.
- Added a dbt test that fails if any feature uses data on or after its index date.

**Surprise:** **29 of the first 36 "diabetes without A1c" gaps were false.** Synthea attaches diabetes *complication* codes, such as "kidney disorder due to diabetes", to some hypertensive patients with no other sign of diabetes.

**What I decided:** complication codes count only if the patient also has an A1c result or a diabetes medication. That left 7 real gaps, and CLAUDE.md was updated.

**Also:**
- The label base rate was 5.9%, above the 3% threshold where I'd asked to be consulted.
- Depression is very sparse (about 12 patients).

## Phase 4: ML

**What happened:** trained gradient boosting on the train snapshot, evaluated it on the test snapshot, and compared it against a "rank by prior ED visits" baseline.

**Surprise:** **35 of the top 50 risk scores were pregnant patients.** Synthea records labor as an emergency visit, so the model was correctly predicting childbirth, which is useless to a care manager.

**What I decided:** exclude obstetric ED admissions (reason code 72892002) from the label, and document why in CLAUDE.md.

**What worked**
- **Claude didn't oversell the model.** It added a bootstrap confidence interval on the AUROC difference and reported that the model was *not clearly better* than the baseline (AUROC 0.559 vs 0.539, CI −0.040 to +0.078).
- That honesty carried into the UI's model card and into the facts sent to the LLM.

**My question:** does `ANTHROPIC_MODEL=claude-haiku-5-5` in `.env` actually get used? Yes: it's read at provider creation, with the same model as the default.

## Phase 5: API and LLM brief

**What happened**
- Built the FastAPI endpoints, the provider abstraction (Anthropic / Ollama stub / Fake), fact building, validation, retry, the SQLite cache, and 23 tests.

**What I decided:** use **structured outputs** (a JSON Schema enforced by the API) instead of forced tool use. The older patterns (forced `tool_choice`, custom `temperature`) return errors on current models.

**What the tests caught**
- **The PHI test caught a real leak.** The first fact said "Age 50–59", but when age was a top SHAP driver, a later fact said "Age = 58". Driver values are now banded too. This is exactly why the "no identifiers in the prompt" test exists.
- Wording bugs:
  - "on within the past month", from converting dates to relative time.
  - "100th percentile", from rounding 99.7. Percentiles are now capped at 99th.

**Something I got wrong:** **a typo in my `.env`** (`ANTROPIC_API_KEY`). Claude found it by checking variable *names* only, never the value. It asked me to fix it rather than editing the file itself. It also added a clear error message for a missing key, so the next person gets "ANTHROPIC_API_KEY is not set" instead of a stack trace.

**The first real brief** (one call, when I asked) passed validation first time:
- Every action cited real facts.
- The outreach message was 69 words.
- The caveats repeated the model's limitations.

**What Claude got wrong:** it estimated about $0.001 per brief. The real output was longer (906 tokens), so it's closer to half a cent. Still trivial, but the estimate was off.

## Phase 6: Frontend

**What happened**
- Built a Vite + React + TypeScript worklist and patient page.
- Dependencies limited to React Router and TanStack Query, with plain CSS.
- Brief fact-ID chips highlight the exact fact the AI cited.

**What worked**
- **Claude checked the UI in a real (headless) browser** instead of trusting the build.
- Before pointing the UI at the real provider, it confirmed that the existing brief was a **cache hit**, so no surprise API call. The log showed zero Anthropic calls.

**What Claude got wrong**
- **It launched Google Chrome from the session without asking.** macOS then warned me the session was "trying to update other applications". That was Chrome's own updater, attributed to VS Code. Nothing was changed, but it should have asked before starting a desktop app. It saved a note to ask first in future.
- Its first automated hover test failed because of its own coordinate bug, not an app bug.

**Surprise:** the worklist showed a **1-year-old at the 99th risk percentile** and **18 patients aged 100–109** (0.9% of patients, vs about 0.03% in the US).

**What I decided:** limit the population to ages 18–99, because both care gaps are adult measures. Then rebuild dbt, retrain and rescore. AUROC rose to 0.589 vs a baseline of 0.555. It is *still* not clearly better than the baseline (CI −0.036 to +0.106).

## Phase 7: README and clean rebuild

**My request:** the README should explain everything simply, without assuming I know the topic, because the point of this project was to learn unfamiliar technologies.

**Surprise:** **the data can't be regenerated.** Claude tested it before cleaning anything:
- Synthea simulates up to the *moment* it runs.
- A rerun pinned to the same date produced an almost entirely different population (1 of 2,297 patients matched).
- Two pinned runs *did* match each other.

**What I decided:** keep the current data. `make data` now skips if data exists (`FORCE=1` overrides), and `make clean` removes only derived files. Pinning the reference date is listed under "What I'd do in production".

**What worked:** `make clean && make all` rebuilt everything in 26 seconds with **identical metrics**, so everything after the raw CSVs is deterministic.

**What Claude got wrong:** the README draft showed an evidence example ("last A1c 7.2% on …") with a value that the real evidence text doesn't include. Claude caught it by checking the SQL before committing.

## After Phase 7: worklist refinements (Sunday)

Using the finished app as a care manager would, I found two workflow problems that no test or metric had flagged.

**1. Patients with gaps were buried.** Only 2 of the 50 highest-risk patients had an open care gap, so the default "highest risk first" order hid the patients with a concrete reason to call.
- **What I decided:** show patients with open gaps first, then by risk.
- **What changed:** a "Sort" option keeps the pure risk ranking one click away. Claude adjusted a test patient's risk so the test can actually tell the two orders apart; before that, the fixtures happened to be in the same order under both.

**2. Calling people who were just seen.** Many high-risk patients had visited only days ago, so there's no point asking them to come in. I suggested a filter rather than a new sort. Claude checked the data before agreeing:
- "Days since last visit" is one of the model's top drivers, because a recent visit often means someone is unwell. 58 of the 148 top-10% risk patients were seen in the last 30 days.
- Of the 48 gap patients, 14 were seen in the last 30 days:
  - 7 had their high BP measured at that visit, so a call is low priority. My intuition was right for these.
  - 5 had a visit that *didn't* close the gap (no A1c, no BP reading), a missed chance that still needs a call.
- Recently discharged patients are exactly who a care manager *should* call.

**What I decided:** a "Last visit" column plus a "Not seen in" filter (any / 30+ / 90+ days), defaulting to "any", so nothing is hidden silently. Labeling each patient with a suggested *call type* ("come in" vs "post-discharge check-in" vs "lab only") went on the production list, because it needs clinically reviewed rules.

**Housekeeping:** `.vscode/` is now gitignored. The DEVLOG draft was generated by Claude at my request (see the note at the top).

## Lessons

1. **Ask the AI to review the spec before coding.** Several real ambiguities, including one contradiction, were caught before any code existed.
2. **"Stop and report surprises" was the most valuable rule.** False diabetes gaps, pregnancy dominating the risk list, toddlers and centenarians, unreproducible data: each would have quietly produced a convincing but wrong demo.
3. **Clinical decisions stayed with me.** Claude proposed options with evidence, I chose, and the definition was updated in CLAUDE.md.
4. **Tests for the things that matter catch real bugs.** The PHI-exclusion test found an actual exact-age leak.
5. **Cost control by design:** caching, a fake provider in tests, tests that fail if a real client is created, and one real call only when I ask.
6. **An honest model is a better demo than an impressive one.** It doesn't beat a simple baseline, and the app says so everywhere.
7. **Use the product, not just the metrics.** The two worklist problems only showed up when I looked at the list as a care manager. The data then confirmed them, and also showed which part of my first idea was too blunt.
8. **The AI's environment can differ from mine.** Its stale PATH and the surprise Chrome launch are reminders to watch what it runs on my machine.
